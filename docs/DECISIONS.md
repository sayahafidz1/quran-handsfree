# Catatan Keputusan Arsitektur (Architecture Decision Records)

## 2026-08-24 — Pemisahan Produk Aplikasi dan Engine Upstream
- **Konteks**: Diperlukan aplikasi Quran Hands-Free yang memanfaatkan kemampuan pengenalan Tilawa.
- **Keputusan**: `quran-handsfree` dibuat sebagai proyek terpisah. Folder clone upstream `../tilawa` tidak dimodifikasi sama sekali.
- **Konsekuensi**: Upgrade engine upstream di masa depan tetap bersih dan pengelolaan lisensi/atribusi jelas.

## 2026-08-24 — Web/PWA & Inferensi di Web Worker
- **Konteks**: Pengenalan audio harus berjalan lokal di perangkat pengguna tanpa membuat antarmuka macet (*UI freeze*).
- **Keputusan**: Menggunakan `@tilawa/core` + `onnxruntime-web` (WASM) yang dieksekusi di dalam Web Worker terpisah. Audio dikonversi ke mono Float32 16 kHz.
- **Konsekuensi**: Kinerja UI tetap lancar 60fps saat inferensi berlangsung.

## 2026-08-24 — Aset Model Dipin & Diabaikan oleh Git
- **Konteks**: Berkas model ONNX (~88 MB) dan JSON kosakata berukuran besar tidak cocok disimpan di version control Git.
- **Keputusan**: Folder `public/tilawa/` menyimpan aset runtime lokal dan didaftarkan di `.gitignore`. Aset dipin versinya dan diverifikasi dengan checksum SHA-256.
- **Konsekuensi**: Ukuran repository tetap ramping dan proses upgrade aset terkontrol dengan aman.

## 2026-08-28 — Penyempurnaan Struktur Modular & Batas Integrasi Tilawa
- **Konteks**: Memastikan arsitektur proyek rapi, terisolasi, dan siap dikembangkan lintas platform tanpa mengaburkan batas antara recognition engine dan domain logic produk.
- **Keputusan**:
  1. Merapikan struktur folder menjadi:
     - `src/app/`: bootstrap dan orkestrasi aplikasi.
     - `src/audio/`: penangkapan audio & resampling.
     - `src/recognition/`: kontrak umum pengenalan suara.
     - `src/recognition/tilawa/`: adapter isolasi untuk `@tilawa/core`.
     - `src/workers/`: background worker untuk eksekusi session ONNX.
     - `src/ui/`: presentasi dan styling antarmuka.
  2. Menegaskan bahwa product logic di masa depan (`discovery -> lock -> verify -> next ayah`) tidak boleh masuk ke dalam `src/recognition/tilawa/`.
  3. Mengonsumsi `@tilawa/core` murni melalui public package API tanpa menyalin source atau mengimpor internal file.
  4. Menunda fitur produk seperti verifier, voice command, dan antarmuka mushaf ke backlog iterasi berikutnya.
- **Konsekuensi**: Arsitektur menjadi sangat terstruktur (*loose coupling*), mudah diuji, dan portabel untuk platform Android nantinya.

## 2026-08-28 — Navigasi Surat dan Ayat Berada di Boundary Produk
- **Konteks**: Pengguna perlu menentukan posisi awal bacaan tanpa melantunkan ayat terlebih dahulu.
- **Keputusan**: Parsing perintah, validasi 114 surat/nomor ayat, dan penguncian anchor ditempatkan di `src/command/` serta `src/quran/`; Tilawa tetap terbatas pada discovery bacaan.
- **Konsekuensi**: `VoiceCommandRecognizer` dapat diganti dengan STT on-device di masa depan tanpa mengubah parser, validator, coordinator, atau source upstream Tilawa.

## 2026-09-04 — Memisahkan Pilihan Ayat User dari Discovery Tilawa
- **Konteks**: Hasil `verse_match` Tilawa dapat datang setelah user memilih surat dan ayat melalui command.
- **Keputusan**: `AnchorCoordinator` menyimpan `selectedVerse` terpisah dari `currentAnchor`. Command memperbarui `selectedVerse`, sementara discovery Tilawa hanya memperbarui anchor.
- **Konsekuensi**: Pilihan user dapat dibaca kembali melalui `getSelectedVerse()` dan tidak berubah saat event `verse_match` diproses.

## 2026-09-04 — Memisahkan Expected Verse dari Detected Verse
- **Konteks**: Produk perlu membandingkan ayat yang dipilih user dengan ayat yang ditemukan recognition engine tanpa mengubah target bacaan.
- **Keputusan**: `src/app/reading/ReadingState.ts` menyimpan `selectedVerse`, `expectedVerse`, dan `detectedVerse`. Seleksi command mengisi dua state pertama; event Tilawa hanya mengisi `detectedVerse`.
- **Konsekuensi**: Hasil deteksi yang berbeda (misalnya `36:10`) dapat diamati tanpa auto-next-ayah atau perubahan target `36:3`.

## 2026-09-04 — Menahan Perpindahan Anchor pada Deteksi yang Tidak Cocok
- **Konteks**: Tilawa dapat mendeteksi ayat lain ketika user telah mengunci target bacaan.
- **Keputusan**: `ReadingState` menghitung `verseMatch` dengan perbandingan exact `surah` dan `ayah`. `AnchorCoordinator` tetap memperbarui `detectedVerse`, tetapi tidak memindahkan anchor aktif jika hasilnya mismatch.
- **Konsekuensi**: Aplikasi tetap menunggu ayat yang dipilih user, sementara hasil discovery yang cocok tetap dapat mengubah anchor seperti sebelumnya.

## 2026-09-04 — Menerima Word Progress Hanya untuk Expected Verse
- **Konteks**: Event `word_progress` Tilawa dapat berasal dari ayat yang berbeda dari target bacaan.
- **Keputusan**: `ReadingState` memvalidasi pasangan `surah`/`ayah` pada progress terhadap `expectedVerse`. Progress yang cocok disimpan untuk UI, sedangkan progress yang berbeda diabaikan tanpa mengubah target atau progress terakhir yang valid.
- **Konsekuensi**: UI tidak menampilkan kemajuan dari ayat lain dan progress valid tetap tersedia melalui `AnchorCoordinator.getWordProgress()`.

## 2026-09-11 — State Machine Reading Session di Product Layer
- **Konteks**: Stage 1 membutuhkan alur eksplisit dari discovery hingga verifikasi ayat berikutnya tanpa menaruh logika produk di adapter Tilawa.
- **Keputusan**: Menambahkan `src/app/reading/ReadingSession.ts` sebagai state machine yang menerima event publik `verse_match` dan `word_progress`. State mismatch mempertahankan ayat aktif, sedangkan progress kata terakhir menentukan `expected_next`; deteksi ayat berikutnya hanya memajukan sesi jika cocok persis.
- **Konsekuensi**: Orkestrasi sesi dapat diuji tanpa model atau browser, dan adapter recognition tetap hanya meneruskan event.

## 2026-09-11 — Navigasi Ayat Menggunakan Metadata Surat
- **Konteks**: Stage 1 membutuhkan ayat berikutnya yang benar ketika ayat selesai, termasuk saat berpindah surat.
- **Keputusan**: Menempatkan `getNextVerse()` di `src/quran/navigation.ts` dan menggunakan `SurahInfo.totalAyahs` sebagai sumber kebenaran. Fungsi mengembalikan awal surat berikutnya pada batas surat dan `null` setelah 114:6.
- **Konsekuensi**: Aturan navigasi dapat digunakan ulang oleh domain lain dan `ReadingSession` tidak perlu menduplikasi logika metadata surat.

## 2026-09-14 — Command Navigation Starts ReadingSession Directly
- **Konteks**: Jalur command sebelumnya meneruskan hasil parser ke `AnchorCoordinator` sebelum memulai sesi bacaan, sehingga navigation state dan recitation discovery tercampur.
- **Keputusan**: Input teks dan voice yang berhasil diparse langsung memanggil `ReadingSession.start({ surah, ayah })`. `AnchorCoordinator` dipertahankan untuk state anchor dan discovery Tilawa, tetapi tidak lagi menjadi dependency jalur command.
- **Konsekuensi**: Command navigation memiliki satu target sesi yang eksplisit dan valid; memulai audio setelah command mempertahankan target tersebut, sementara command invalid tetap tidak mengubah sesi.

## 2026-09-14 — ReadingSession Owns Application Recognition Routing
- **Konteks**: Event `verse_match` sebelumnya diteruskan ke `ReadingSession` dan `AnchorCoordinator`, sehingga dua state consumer dapat bereaksi terhadap hasil Tilawa.
- **Keputusan**: `handleRecognitionEvent()` meneruskan `verse_match` dan `word_progress` hanya ke `ReadingSession.handleEvent()`. UI menampilkan posisi dari snapshot `ReadingSession`; `AnchorCoordinator` tidak lagi dipanggil oleh jalur recognition aktif.
- **Konsekuensi**: Discovery langsung, mismatch protection, dan word progress memiliki satu sumber kebenaran tanpa mengubah adapter Tilawa atau integrasi ONNX.

## 2026-09-14 — Remove AnchorCoordinator
- **Konteks**: Setelah command navigation dan recognition routing dipindahkan ke `ReadingSession`, `AnchorCoordinator` tidak lagi memiliki consumer runtime maupun tanggung jawab yang tersisa.
- **Keputusan**: Menghapus `AnchorCoordinator`, tipe anchor legacy, export coordinator, serta pengujian khususnya. `ReadingSession` menjadi satu-satunya pemilik state navigasi dan state reading aplikasi.
- **Konsekuensi**: Arsitektur runtime tidak memiliki dependency anchor legacy; command parser dan recognizer tetap menjadi API command yang aktif, sedangkan discovery Tilawa tetap masuk melalui `ReadingSession`.

## 2026-09-19 — Reading Status Presentation Uses Session Snapshots
- **Konteks**: Pengguna perlu membedakan seluruh state sesi serta memahami mismatch, repeat, dan skip tanpa posisi bacaan berpindah.
- **Keputusan**: `src/ui/readingStatus.ts` menjadi mapping presentasi terpusat dari `ReadingSessionSnapshot` ke label dan pesan. `QuranReader` dan anchor memakai mapping yang sama; UI tidak menambahkan state machine atau recovery logic.
- **Konsekuensi**: State `idle`, `discovering`, `locked`, `tracking`, `expecting_next`, `mismatch`, dan `completed` memiliki feedback yang konsisten. Pesan mismatch menjelaskan expected/detected, sementara transisi recovery tetap ditentukan oleh `ReadingSession`.

## 2026-09-19 — Basic Reader Controls Use One Command Path
- **Konteks**: Reader membutuhkan kontrol hands-free dasar tanpa mencampur pengenalan command dengan pengenalan Tilawa.
- **Keputusan**: Parser command menghasilkan command navigasi ayat atau kontrol deterministik. Teks dan voice memakai handler aplikasi yang sama, sementara transisi posisi dan sesi tetap dimiliki `ReadingSession`.
- **Konsekuensi**: `start`, `current`, `repeat`, `next`, `previous`, `stop`, dan `resume` konsisten dengan UI manual; command invalid tidak mengubah snapshot sesi.

## 2026-11-11 — word_index Adalah Cursor Zero-Based; Akhir Ayat Ditentukan dari matched_indices
- **Konteks**: Log nyata Al-Ikhlas 112:1-2 menunjukkan sorotan berhenti sebelum kata "Ahad" dan sesi masuk `mismatch` saat Zipformer berpindah ke 112:2. Aplikasi menganggap `word_index` one-based (jumlah kata selesai) dan menyatakan ayat selesai saat `wordIndex >= totalWords`. Audit source `@tilawa/core` 0.4.0 menunjukkan `word_index` adalah posisi cursor alignment zero-based yang selalu lebih kecil dari `total_words`, sedangkan `matched_indices` (kata dengan verdict `ok`/`unsure`) dihitung terpisah.
- **Keputusan**: `TilawaAdapter` meneruskan `matched_indices`. `WordProgress` menyimpan `matchedIndices`. Sorotan kata memakai cursor zero-based tanpa `- 1`. Ayat dianggap selesai (`hasReachedVerseEnd`) ketika kata terakhirnya ada di `matched_indices`. `ReadingSession` memperlakukan `verse_match` atau `word_progress` untuk ayat tepat setelah ayat aktif sebagai transisi normal, bukan `mismatch`; ayat yang dilompati, diulang pada target expected-next, atau berasal dari ayat lain tetap tidak memajukan sesi. (Bagian transisi "ayat tepat setelah ayat aktif" ini digantikan oleh keputusan 2026-11-11 berikutnya: perpindahan ayat hanya setelah ayat aktif selesai.)
- **Konsekuensi**: "Ahad" tersorot dan sesi berpindah ke ayat berikutnya tanpa mismatch pada log Al-Ikhlas. Aplikasi tidak lagi bergantung pada asumsi `word_index >= total_words`, yang tidak pernah dihasilkan upstream. Definisi `word_index` berasal dari pembacaan source upstream dan perlu diuji ulang saat memperbarui versi `@tilawa/core`.

## 2026-11-11 — Perpindahan Ayat Ketat: Hanya Setelah Ayat Aktif Selesai, dan Status Selesai Menempel
- **Konteks**: Keputusan sebelumnya mengizinkan sesi mengikuti `verse_match`/`word_progress` untuk ayat tepat setelah ayat aktif walau ayat aktif belum selesai. Audit source `@tilawa/core` 0.4.0 menunjukkan cursor engine memang dapat masuk ayat berikutnya sebelum kata terakhir ayat sebelumnya dinilai, sehingga pada ayat panjang (misalnya Al-Bayyinah) membaca dua-tiga kata lalu ayat berikutnya akan melompatkan sorotan melewati banyak kata. Aturan itu juga bertentangan dengan prinsip di `ARCHITECTURE.md` bahwa hanya ayat yang diharapkan yang boleh memajukan sesi. Audit yang sama menemukan bahwa `matched_indices` adalah snapshot alignment terbaru (bukan riwayat), kata terakhir ayat tidak dijamin memperoleh verdict `ok`/`unsure`, dan `word_progress` hanya mewakili ayat tempat cursor berada.
- **Keputusan**: `ReadingSession` hanya memajukan sesi ke `expectedNextVerse`, yang baru terisi setelah ayat aktif selesai (`hasReachedVerseEnd`: kata terakhir ada di `matched_indices`). `verse_match` untuk ayat lain sebelum itu menjadi `mismatch`, dan `word_progress` ayat lain diabaikan. Status selesai menempel: jika snapshot berikutnya tidak lagi memuat kata terakhir (revisi verdict atau pengulangan kata), `expectedNextVerse` dipertahankan dan hanya sorotan kata live yang kembali mengikuti snapshot, sampai sesi berpindah ayat. Tidak ada toleransi "boleh lompat beberapa kata sebelum akhir" dan tidak ada mundur ke ayat sebelumnya; kebutuhan mengulang kata sebelumnya di ayat yang sama sudah tercakup karena `word_progress` ayat aktif selalu menimpa posisi kata.
- **Konsekuensi**: Perpindahan ayat dapat diprediksi dan tidak melewati kata. Risiko yang diketahui: bila engine tidak pernah memasukkan kata terakhir ke `matched_indices` walau bacaan benar, sesi tertahan sampai kata terakhir dibaca ulang. Toleransi (misalnya boleh kurang satu kata) atau kontrol manual hanya dipertimbangkan setelah ada log nyata yang menunjukkan hal itu sering terjadi. Bentuk waqaf kata terakhir ayat dinyatakan tersimpan di korpus upstream menurut spesifikasinya, tetapi data korpus lengkap belum diverifikasi.

## 2026-11-11 — Restart Discovery Saat Surat Selesai; Basmalah Sebelum Surat Berikutnya Bukan Mismatch
- **Konteks**: Setelah menyelesaikan Al-Ikhlas, membaca Al-Falaq (dengan atau tanpa bismillah) tidak membuat aplikasi bergerak. Sesi menunggu persis 113:1 (aturan ketat), sedangkan engine memakai `stayOnSurah: true` sehingga tidak kembali mencari sendiri kecuali lewat event `completed` atau diam sekitar 8 detik. Basmalah juga berpotensi terdeteksi sebagai Al-Fatihah 1:1, yang akan menjadi `mismatch` dan mengunci engine pada Al-Fatihah.
- **Keputusan**: `ReadingSession` meminta restart discovery lewat `onDiscoveryRestart()` (a) satu kali saat ayat terakhir sebuah surat selesai, yaitu ketika `expectedNextVerse` baru terisi dengan ayat 1 surat lain, dan (b) saat `verse_match` 1:1 diterima sementara `expectedNextVerse` adalah ayat 1 surat selain Al-Fatihah; pada kasus (b) event diabaikan, bukan `mismatch`, dan `detectedVerse` tidak diubah. `app.ts` mengeksekusi permintaan itu dengan `recognition.reset()` hanya saat mendengarkan. Session tetap tidak mengakses engine, dan core `@tilawa/core` tidak diubah.
- **Konsekuensi**: Alur Al-Ikhlas ke Al-Falaq tidak lagi bergantung pada event `completed` upstream. Risiko yang diketahui dan belum diuji: `reset()` membuang konteks decoder sehingga awal surat berikutnya yang dibaca persis saat reset dapat terpotong; basmalah yang terdeteksi berulang dapat memicu beberapa reset selama diucapkan; dan belum terbukti engine memang mengirim basmalah sebagai 1:1. Pembacaan surat lain selain surat berikutnya tetap `mismatch` sampai ada kontrol navigasi atau frasa isti'adzah untuk kembali mencari (belum dibuat).

## 2026-11-15 — "Pencarian Baru Diizinkan": Surat Selesai, Jeda Hening, Basmalah
- **Konteks**: Skenario shalat sunnah (surat belum selesai, ruku'/sujud, Al-Fatihah rakaat berikutnya, lalu mis. An-Naba 78:31 tanpa bismillah) membuat aplikasi `mismatch` permanen karena `ReadingSession` hanya menerima ayat berikutnya yang tepat. Setelah Al-Fatihah selesai pun, aturan lama menunggu 2:1 sehingga 78:31 menjadi `mismatch`, padahal engine sudah mencari ulang (Fitur 1).
- **Keputusan**: `ReadingSession` punya penanda internal `discoveryOpen`: deteksi `verse_match` berikutnya mengunci di mana pun pembaca berada (tanpa `mismatch`), lalu penanda padam. Dibuka oleh (a) selesainya ayat terakhir sebuah surat (menggantikan aturan 2026-11-11 bahwa surat lain tetap `mismatch` sesudahnya; ayat 1 surat berikutnya tetap terkunci seperti biasa), (b) `handlePause()`, dipanggil `app.ts` bila 20 detik tidak ada event pengenalan sama sekali (diam sungguhan; `InactivityTimer`, sekali jalan sampai ada event lagi; membaca ayat yang salah tetap menghasilkan event, jadi `mismatch` bukan jeda) dan juga meminta reset engine, dan (c) `verse_match` dengan `basmala: true` untuk ayat 1 (hanya jalur Tilawa 1.0, dari `prefix: "basmala"`). `handlePause()` tidak melakukan apa-apa sebelum ada ayat terkunci, sehingga target manual tetap ketat. Posisi yang tampil di UI dipertahankan sampai ada kunci baru. Di dalam satu surat, aturan ketat tidak berubah.
- **Konsekuensi**: Isti'adzah, "aamiin", dan frasa shalat tidak punya pemicu sendiri (1.0 tidak mengirimnya sebagai event); celah itu ditutup oleh surat selesai dan jeda. Risiko diketahui: setelah jeda/surat selesai, derau atau bacaan lain dapat terkunci ke ayat yang salah sampai pembaca memperbaikinya; 20 detik adalah angka awal yang perlu dikalibrasi dari tes nyata. Revisi hari yang sama: versi pertama (10 detik, `mismatch` tidak dihitung aktif) terbukti salah pada tes nyata, karena membaca surat lain terus-menerus membuka pencarian berulang dan sesi melompat-lompat; karena itu jeda kini hanya diam sungguhan. Derau yang menghasilkan event dapat menunda jeda.

## 2026-11-16 — Self-Host Tilawa 1.0 untuk Tujuan APK Offline
- **Konteks**: Tujuan akhir aplikasi adalah APK yang berjalan tanpa internet. Jalur 1.0 awal memuat model dari `tilawa.dev` dan WASM dari jsDelivr (butuh internet). Cloudflare Pages/Workers membatasi sekitar 25 MiB per aset, jadi model penuh 68 MB tidak bisa disajikan dari sana. Upstream mendokumentasikan self-hosting dan lisensi CC BY 4.0 mengizinkan redistribusi dengan atribusi.
- **Keputusan**: Dua mode, dipilih `VITE_TILAWA_V1_ASSETS`: `remote` (bawaan, perilaku lama, aman untuk deploy Cloudflare) dan `local` (semua file dari origin aplikasi lewat `npm run setup:v1`, model penuh bawaan, penyimpanan model di memori, tanpa cache service worker). Atribusi CC BY 4.0 ditambahkan di layar "Tentang & Lisensi", `ATTRIBUTION.txt`, dan `THIRD_PARTY_NOTICES.md`. Bawaan engine tidak diubah.
- **Konsekuensi**: Mode lokal tidak untuk deploy Cloudflare dengan model penuh. Di web (bukan APK) pengguna tetap mengunduh model dari server host tiap sesi, karena cache sengaja tidak dipakai. Kebenaran jalur ini belum diuji (tidak ada build atau unduhan di lingkungan pembuatan); lihat daftar "Belum diverifikasi" di `TILAWA_INTEGRATION.md` bagian 7. Pemilihan model untuk APK (full vs lite) menunggu pengukuran di ponsel.

## 2026-11-15 — Kunci Sementara untuk Ayat Kembar; Kata Terlewat Tetap Diikuti
- **Konteks**: Log nyata Tilawa 1.0 (membaca Al-Baqarah 2:214 dan berhenti di "walamma") menunjukkan engine `ambiguous` untuk 2:214 dan 3:142 yang identik sampai kata ke-6, lalu `locked` ke 3:142 saat bukti kata ke-7 hampir tidak ada, dan baru mengoreksi ke 2:214 sekitar 4,8 detik audio kemudian. `ReadingSession` menolak koreksi itu sebagai `mismatch`. Event `locked` pertama tidak membawa `spanHold` atau `relocated`, jadi tidak ada sinyal engine yang bisa ditunggu. Log yang sama (29:2, 29:3) menunjukkan engine mengikuti posisi bacaan dan menandai kata yang dilewati lewat event `checker` `omitted_word`, bukan menahan posisi.
- **Keputusan**: (1) Kunci hasil discovery (awal, setelah jeda, setelah surat selesai) bersifat sementara (`provisional`) di `ReadingSession`: selama ayatnya belum selesai, `verse_match` untuk ayat di **surat lain** mengunci ulang ke ayat itu (status `locked`, progress kata dikosongkan) alih-alih `mismatch`. Kunci menjadi permanen saat ayat selesai (`hasReachedVerseEnd`), saat maju ke ayat berikutnya yang diharapkan, atau lewat perintah `current`/`start`. Lompatan ke ayat lain dalam surat yang sama tetap `mismatch` (tes lama Al-Bayyinah dipertahankan), dan target manual tidak pernah sementara. (2) Kata yang dilewati di tengah ayat tidak menahan sorotan; sorotan mengikuti kata yang dibaca, aturan ketat tetap pada perpindahan antar ayat. Pewarnaan kata terlewat (dari `checker`) sengaja ditunda sampai tes nyata menunjukkan perlu.
- **Konsekuensi**: Bacaan keliru di awal ayat dapat memindahkan kunci sampai ayat itu selesai. Aturan ini ada di `ReadingSession` sehingga juga berlaku di jalur 0.4.0 (dampaknya kecil karena `stayOnSurah`). Belum terbukti: keluhan "berhenti sebelum kata terakhir lalu ayat maju sendiri" tanpa membaca ayat berikutnya; menunggu log run 29:4. Posisi engine pada kata terakhir tidak selalu berarti kata itu diucapkan (checker dapat menandainya `omitted_word` sesaat kemudian).

## 2026-11-13 — Evaluasi Tilawa 1.0 di Branch Terpisah, 0.4.0 Tetap Default
- **Konteks**: Log nyata menunjukkan dua celah 0.4.0 yang relevan dengan tujuan aplikasi (membaca tanpa memegang ponsel, termasuk shalat sunnah): isti'adzah di tengah sesi terbaca sebagai An-Nahl 16:98, dan setelah jeda engine kembali ke discovery sementara `stayOnSurah: true` membuatnya macet sampai idle ±8 detik; surat belum selesai lalu Al-Fatihah rakaat baru menjadi `mismatch` permanen. Tilawa 1.0 (rc, Preview) menangani frasa shalat dan basmalah di tracker dan melaporkan state `locked/ambiguous/lost`.
- **Keputusan**: Dibuat branch `eval/tilawa-1.0` dengan jalur engine kedua yang dipilih `VITE_TILAWA_ENGINE=v1`. Jalur 0.4.0, `ReadingSession`, dan aturan ketat tidak diubah; 1.0 dipetakan ke kontrak `verse_match`/`word_progress` yang sama lewat mapper murni (lihat `TILAWA_INTEGRATION.md` bagian 6). Core Tilawa tidak dimodifikasi. Fitur 2 (deteksi isti'adzah) ditunda sampai hasil evaluasi.
- **Konsekuensi**: Tidak ada perubahan perilaku pada `main`. Branch ini tidak boleh di-merge sebelum evaluasi (daftar skenario di `NEXT_STEPS.md` bagian 5) menunjukkan 1.0 lebih baik. Risiko yang diketahui: rc masih Preview (model card: 7 dari 13 target terpenuhi, kecepatan di ponsel belum diukur), model 25-68 MB dan butuh internet, segmentasi kata `ref-v2` belum diverifikasi terhadap konten UI, pemetaan "ayat selesai" masih rancangan awal.

## 2026-11-17 — Jeda Hening Dipersingkat dari 20 ke 10 Detik
- **Konteks**: 20 detik dinilai pemilik proyek terlalu lama untuk skenario memasak dan shalat sunnah. Versi 10 detik pertama (2026-11-15) gagal karena `mismatch` ikut dihitung sebagai aktivitas dan membuka pencarian berulang; revisi 20 detik hanya menghitung hening sungguhan.
- **Keputusan**: `PAUSE_MS` di `src/app/app.ts` menjadi `10_000`. ## 2026-11-17 — Persiapan Model Otomatis, Mikrofon Otomatis dari Navigasi, dan Mengingat Pilihan `lite`
- **Konteks**: Navigasi (Buka ayat, Buka juz, Kembali ke posisi) dan perintah `open` hanya menyetel posisi bacaan; `startListening()` juga diam-diam berhenti bila model belum siap, sehingga tanpa menekan "Siapkan pengenalan" lalu "Mulai mendengarkan" tidak ada yang berjalan. Selain itu, cadangan `lite` belum mengingat pilihannya sehingga ponsel lemah selalu mencoba `full` dulu.
- **Keputusan**:
  1. Model dimuat otomatis saat halaman dibuka (`beginPreparing()`), dengan status teks dan bar loading animasi; bila gagal, tombol berubah menjadi "Coba lagi".
  2. `requestListening()` dipanggil dari Buka ayat, Buka juz, Kembali ke posisi, perintah `open`, dan `start`/`resume`. Bila model sudah siap mikrofon langsung menyala; bila masih memuat, permintaan menunggu dan mikrofon menyala saat siap. Setelah "Berhenti" manual, Buka ayat menyalakan mikrofon lagi. Izin mikrofon yang ditolak menampilkan pesan, tombol manual tetap ada. Logikanya di `listenGate.ts` (murni, diuji).
  3. Setelah cadangan `lite` berhasil, worker menyimpan penanda di Cache API (`tilawa-v1-prefs`) dan `chooseStartTier()` langsung memakai `lite` pada peluncuran berikutnya (mode `remote` saja).
- **Konsekuensi**: Setiap pengunjung baru mengunduh model otomatis (68 MB untuk `full`, 25 MB untuk `lite`), termasuk di data seluler, tanpa pilihan untuk menolak; unduhan berikutnya diambil dari cache. Hal ini berlaku juga untuk engine 0.4.0 bila dipilih. Mikrofon otomatis setelah model selesai dimuat belum diuji di iOS Safari (aturan gestur lebih ketat). "Buka ayat saat sedang mendengarkan" tetap seperti sebelumnya (hanya memindahkan posisi). Untuk mencoba `full` lagi di perangkat yang tersimpan `lite`, hapus data situs di browser.
